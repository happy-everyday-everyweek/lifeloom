# 对齐状态（更新至 2026-09-13）

项目：Lifeloom——插件化的模拟人生类游戏（开源）。玩家在游戏中是一个人；玩法（纯自由沙盒或带目标）由玩家装载的插件决定，系统插件面向纯自由。

## 已定要点

- 目标：高自由度、高可玩性；开源；第一个可玩版本的质量门槛＝足够的可玩性。
- 玩家与开局：玩家=一个人；开局由用户创建一个新的人实例作为自身、进入游戏；中途更换被体验者由三方插件提供（系统不提供）。
- 玩法：沙盒或目标玩法由玩家装载的插件决定；系统插件面向纯自由，便于用户快速改造出想要的玩法。
- 实例：生物（人、动物）可执行动作；物体不能执行动作、只能作动作的附着者；均可附着参数（参数也可附着到机制）。人可以“进入”为被体验实例；动物不可以；所有人的可执行动作与玩家所扮演的人一致。
- 注册规则：注册新参数不需要授权；不能新增顶层分类，新分类必须归入人、动物或物品；新动作可注册（细节待插件细谈）。
- 时间与 NPC：动作驱动——无动作则游戏内时间静止；执行动作时按动作声明的时长（可变、插件提供）流逝；期间可调倍率，1 倍速可与现实同速；NPC 与玩家时间严格同步，仅在时间流逝时可活动（见 docs/adr/0004）。
- 动作执行：由动作插件负责；时间流逝中的操作细节（排队、打断）由动作插件设计；支持深度自定义（三方插件亦可）。
- AI：不是单一插件，能力分布在系统插件各处（如动作插件向 UI 插件声明弹性动作输入框）；轻量＝辅助（游戏不是纯 AI 游戏）；经在线接口访问，服务端由用户自己配置（开源项目最初约定）；另有 AI 插件仅作请求代理，保护用户密钥不被三方插件直接接触。
- 跨端流转：独立插件；范围含存档、插件、远程访问等；同一局域网下要求即时流畅（例如手机打开即同步桌面进度、直接继续）。
- 开发方式：先把核心做完 → 一个插件一个插件地开发（Axiom 先设计完善底层插件：不含任何玩法、只提供标准化能力）→ 之后按机制逐个由用户指示、逐步开发；Android 与桌面同时推进。
- 平台与技术：Android + 桌面；Java 非硬要求、尽可能满足（开发人群大、上手容易、性能较好）；初版核查见 docs/技术核查-Java插件装载与热装载.md。
- 架构：见 docs/adr/0001——核心=极薄宿主；一切功能皆插件；存档、时间等均由插件提供。
- 装载：见 docs/adr/0002——运行时装载必达；整体替换必达；数据不断档。
- 权限：见 docs/adr/0003 与 0005——机制、钩子、签名、跨机制修改授权、冲突检测；权限决策与提示由独立系统插件承担（核心只保留极薄闸门原语）。
- 画面：B（界面 + 轻 2D 视图）。
- 底层系统插件（首批）：存档、UI（核心 UI 能力 ↔ 标准化声明式 UI 的桥；三方一般经系统插件间接使用，直接使用需权限）、动作（执行、注册管理、可执行判定、执行钩子）、钩子管理、地图、NPC（行为）、AI（请求代理）、跨端流转、权限（放行与提示；独立插件，M2 已实现）……清单待扩展。原则：每个插件要足够小、职责划分必须特别明确。
- 仓库：Lifeloom。本地 git 历史已建立；远端 GitHub 仓库 happy-everyday-everyweek/lifeloom 已创建并推送（文档、M0 骨架、Android 骨架均已入库）。
- 词表：见 CONTEXT.md。
